# OpenAI Symphony 的产品表面与对话边界

核验日期：2026-08-09

官方仓库快照：[`f8e8b8a`](https://github.com/openai/symphony/tree/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7)

## 结论

- **Observed：** Symphony 的规范对象是长期运行的 coding-agent 编排服务：持续读取 Tracker、为 Issue 建立隔离 Workspace，并在其中运行 Agent Session。规范直接称其为 `scheduler/runner and tracker reader`，核心职责还包括并发、重试、重协调和清理，不只是一次性任务派发。[SPEC：问题与边界](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L18-L58)
- **Observed：** Rich Web UI 是明确非目标；人类可读的 Status Surface 是可选项，并且不能成为 Orchestrator 正确性的依赖。[SPEC：非目标与可选状态面](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L60-L68), [SPEC：组件](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L93-L116)
- **Observed：** 当前 Elixir 参考实现没有对话 UI。它自动创建 Codex Thread、提交由 `WORKFLOW.md + Issue` 生成的 Turn，并把 Agent 事件回传给 Orchestrator；如果 Codex 需要无法自动回答的用户输入，则把运行标为 blocked，而不是在 Dashboard 中开启聊天。[AgentRunner](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/agent_runner.ex#L88-L153), [App Server client](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/codex/app_server.ex#L307-L366), [用户输入处理](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/codex/app_server.ex#L688-L708)
- **Inference：** “Tracker 驱动的轮询、派发、执行与重协调守护进程”是准确定位；“聊天产品”不是。Conversation 是 Codex App Server 的内部执行协议和上下文，不是 Symphony 原始产品中的主要人机交互对象。

## 对 Symphoneer 的含义

- **Inference：** 持久执行活动、Attempt 历史或“在 Codex 中继续”属于 Workbench 产品层扩展，不是 Symphony 必选 UI。
- **Observed：** 官方恢复依赖 Tracker 与保留的 Workspace；内存调度状态与运行中 Session 不要求跨重启恢复，也不要求持久化完整 Conversation。[SPEC：重启恢复](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L1689-L1704)

本快照支持 [`../design-docs/product-boundary.md`](../design-docs/product-boundary.md) 与 [`../design-docs/system-boundaries.md`](../design-docs/system-boundaries.md)；不自动修改产品决定。早期无 commit 的定位长文已 stub：[`2026-07-30-symphony-runtime-boundaries.md`](2026-07-30-symphony-runtime-boundaries.md)。

## Verification、完成、Blocked 与重试契约

- **Observed：没有独立的固定 Verification 阶段。** SPEC 的 Run Attempt 只定义 `PreparingWorkspace → BuildingPrompt → LaunchingAgentProcess → InitializingSession → StreamingTurn → Finishing` 及成功/失败/超时/停滞/重协调取消等结果，没有 Verifier 组件或 Verification 状态。规范把 validation 规则放在 repo-defined Policy Layer；`before_run` / `after_run` 仅是可选 Workspace hook，且 `after_run` 失败会被记录后忽略，因此它也不是强制验收门。[SPEC：组件与 Policy Layer](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L93-L124), [SPEC：Run Attempt 生命周期](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L676-L692), [SPEC：Workspace hooks](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L903-L926)
- **Observed：参考 Workflow 要求 Agent 自己执行验证。** 它要求 Agent 把 Issue 中的 `Validation` / `Test Plan` / `Testing` 当作必须验收输入，在实现期运行范围所需的测试，检查 PR checks，并只在验证全部通过后转入 `Human Review`。这是 `WORKFLOW.md` Prompt 驱动的 Agent 行为，不是 Agent 结束后 Runtime 再运行的第二套固定验证。[参考 Workflow：验收输入](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L83-L97), [参考 Workflow：执行与验证](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L199-L237), [参考 Workflow：交接门槛](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L265-L290)
- **Observed：Worker 成功不等于任务 Done。** 任务是否完成由 Tracker 的 workflow-defined 状态表达；成功运行可以停在 `Human Review` 等交接状态。每个 Turn 正常完成后，Agent Runner 重读 Tracker；若 Issue 仍是 active 且 routable，则在同一 Thread/Workspace 继续下一 Turn，直到状态变化或达到 `max_turns`。Worker 正常退出后 Orchestrator 仍会在约 1 秒后重读状态，避免把“Turn 结束”误当成“任务完成”。[SPEC：成功与交接边界](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L36-L44), [SPEC：继续运行](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L662-L674), [AgentRunner：Turn 后重读 Tracker](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/agent_runner.ex#L101-L169)
- **Observed：Blocked 不是通用业务工作流阶段。** SPEC 只要求 user-input/approval 策略必须由实现记录，且不得无期等待；可以失败、向 operator 暴露、通过批准通道满足或自动处理。当前 Elixir 参考实现选择将无法自动回答的 input/approval 保存在内存 `blocked` map：停止 running/retry，保持 claim 以防重复派发；当 Tracker 变为 terminal 时清理并释放，变为 non-active、unroutable 或不可见时释放。参考实现没有在这里定义一个通用的“回答后恢复”命令。[SPEC：User input 是 implementation-defined](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L1065-L1082), [SPEC：User-input-required 策略](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L1133-L1139), [App Server：转为 input/approval error](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/codex/app_server.ex#L493-L547), [Orchestrator：记录 Blocked 并停止重派](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/orchestrator.ex#L757-L828), [Orchestrator：Blocked 重协调](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir/orchestrator.ex#L335-L473)
- **Observed：重试分为正常继续与失败恢复。** Worker 正常退出后用 1 秒固定延迟做 continuation check；异常退出、Turn 错误、超时或停滞则以 `min(10000 * 2^(attempt - 1), max_retry_backoff_ms)` 指数退避。计时器触发时必须重读该 Issue：只有仍 active 且 routable 才重派；terminal 则清理 Workspace 并释放 claim，non-active/unroutable/不可见则仅释放。[SPEC：Retry 与 backoff](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L790-L817), [SPEC：Stall 与状态重协调](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L819-L839), [SPEC：失败恢复](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L1668-L1687)
- **Clarification：** Tracker 中的 `blocked_by` 是任务依赖/派发门禁元数据；参考实现的 runtime `blocked` 是 input/approval 无法自动处理时的 operator-attention 状态，两者不是同一契约。

## Diff 与 Pull Request 默认行为

- **Observed：** Symphony Core 不直接规定 commit、push 或创建 PR；规范把自身边界限定为 scheduler/runner 与 tracker reader，并把 Ticket/PR 元数据写入交给 Workflow 驱动的 Coding Agent 及其工具。[SPEC：核心边界](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L36-L44), [SPEC：Tracker 写入边界](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/SPEC.md#L1309-L1321)
- **Observed：** Elixir 示例的默认 `WORKFLOW.md` 选择了完整 GitHub 交付策略：Agent 提交并推送代码、创建或更新 PR、把 PR 链接附到 Issue、等待检查与反馈通过，再将 Issue 转入 `Human Review`。仓库附带的 `commit`、`push`、`pull`、`land` skills 分别实现提交、发布 PR、同步主分支和最终 squash merge；安装说明将复制这些 skills 标为可选，因此这是参考 Workflow 的策略，不是 Symphony Core 的必选能力。[默认 Workflow](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L199-L251), [安装说明](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/README.md#L38-L53), [commit skill](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/commit/SKILL.md#L18-L54), [push skill](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/push/SKILL.md#L26-L56), [pull skill](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/pull/SKILL.md#L12-L36), [land skill](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/land/SKILL.md#L26-L41)
- **Observed：** Bundled Workflow 和 skills 没有要求 Draft PR，也没有执行 Draft/Ready 状态转换；新 PR 的实际命令是 `gh pr create --title "$pr_title"`，未传 `--draft`。[push skill：PR 创建命令](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/push/SKILL.md#L80-L100)
- **Inference：** 按该命令的通常语义，参考 Workflow 默认创建可供审查的非 Draft PR；仓库中没有另行声明 Draft PR 默认策略。
- **Observed：** 人工审查面是外部 GitHub PR：Workflow 要求读取顶层评论、Inline Review 和 Review 状态，人工批准后再把 Tracker Issue 移到 `Merging`，随后由 `land` skill 合并。Bundled Dashboard 仅展示运行、阻塞、重试、Token、最近 Codex 更新和 JSON 详情，不提供 Diff 或 PR Review 视图。[PR feedback 协议](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L171-L185), [Human Review 流程](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/WORKFLOW.md#L244-L251), [Dashboard：运行与阻塞表面](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/elixir/lib/symphony_elixir_web/live/dashboard_live.ex#L129-L281)
- **Inference：** 因此，人类预期在 GitHub PR 中查看完整代码 Diff、检查结果和 Review Threads；Tracker 承载工作状态与交接，Symphony Dashboard 只负责运行观测。`commit` skill 中的本地 `git diff`/`git diff --staged` 是 Agent 提交前的范围校验，不是人类 Diff 审查界面。[README：交付证据与接受后合并](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/README.md#L1-L19), [commit skill：本地 Diff 检查](https://github.com/openai/symphony/blob/f8e8b8a670c799f6e0ade7a8c25c4bf4a4a56ec7/.codex/skills/commit/SKILL.md#L18-L34)
